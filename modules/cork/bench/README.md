# cork bench

A benchmark of guest code for the translator: one 32-bit Windows program in two builds,
[`bin/bench-x87.exe`](bin/bench-x87.exe) (x87 arithmetic, as compilers of the era emitted it) and
[`bin/bench-sse.exe`](bin/bench-sse.exe) (scalar SSE2), built from [`src/`](src/) with clang for the
MSVC ABI and no C runtime. Each run executes one workload and exits with its checksum.

| workload | what it is |
|---|---|
| `vm` | a stack-machine interpreter over generated bytecode: one switch, a jump table, a different target nearly every time |
| `entities` | 4 096 objects of 24 classes, each with its own virtual `update`, `think` and `collide`, stepped in mixed order and bucketed into a grid |
| `math` | quaternion bones, four-bone skinning, transforms, renormalised normals, four lights, triangle culling |
| `path` | A* on a 128×128 grid with a binary heap |
| `lz` | LZ77 with hash chains both ways, a table CRC, a Huffman code built, packed and decoded |
| `containers` | a string-keyed hash table, sorts instantiated for several types and orders, binary search, an LRU list |
| `spread` | 512 distinct functions calling one another directly and through a table in a data-driven order |
| `api` | kernel32 and msvcrt calls in a frame's proportions between short stretches of the program's own work |

A checksum does not depend on who ran the program: no time, handle, thread id or address goes into
it. [`native/peload.c`](native/peload.c) is a small 32-bit Linux loader: it maps the same
executable at its base, binds its imports to functions of its own and runs it on the processor. So
the reference checksums in [`expected.json`](expected.json) are what the hardware computed from the
same machine code the engine translates, and a run with `--native` also reports how many times
slower the engine was.

    node modules/cork/bench/build.mjs          # clang, lld-link, llvm-dlltool
    node modules/cork/bench/run.mjs            # every workload, both builds
    node modules/cork/bench/run.mjs --native --only spread,vm --reps 3
    node modules/cork/bench/run.mjs --cork '{"callTargets":true}'

`run.mjs --help` prints its header comment. A run's time includes translation and the cold code
before it, which a program pays too.

## In the browser

A change is judged by its figures from Chromium, not Node: the engine runs in Chromium, whose V8 is
newer and inlines and tiers wasm differently, and there it is the product's bundle with its
translation worker. [`browser/`](browser/) runs the same workloads there, each run in a fresh tab
and a dedicated worker of a production-style bundle (minified, the diagnostic instruments folded
out):

    node modules/cork/bench/browser/build.mjs '{"head":"."}'       # bundles/head from this checkout
    node modules/cork/bench/browser/suite.mjs '{"head":{}}'

At a workload's own iterations a run is a few hundred milliseconds, and the load, the translation
and the engine's compiles are a quarter to most of it: such a run measures the start. `--scale 10`
runs ten times the iterations, which leaves them a few per cent, so it measures the translated
code. With `bin/peload` (Linux) the processor runs the same workloads and its rate is shown
alongside, which gives the loss against the hardware:

    node modules/cork/bench/browser/suite.mjs '{"head":{}}' --scale 10 --reps 3

Runs at `--scale 10` differ by about a tenth from one rep to the next; runs at their own iterations
differed by up to two thirds.

[`browser/build.mjs`](browser/build.mjs) takes any number of checkouts, so an A/B is two bundles,
`'{"base":"../base","new":"."}'`, and two configurations naming them. A configuration's `cork` is
the translator's configuration, so a flag is A/B'd on one bundle. Both builds of every workload,
two reps of each, take about a minute and a half. The browser is `CDP_TEST_CHROME` or the first one
[`tools/cdp_test`](../../../tools/cdp_test) finds.
