# x86-64

Plan, work started 2026-10-26.

Today only 32-bit PE images run; the loader refuses any other machine.

## Decisions

- **Address space:** a 4 GiB window first. Pointers are 64-bit, every guest page lies below
  4 GiB, and an image whose preferred base is above it (0x140000000 by default) is relocated
  down through its relocations. It runs in every browser, Safari and iOS included, with memory
  accesses as cheap as 32-bit code's. `memory64` comes later as a variant, for browsers that
  have it and programs that need more than 4 GiB.
- **First targets:** a freestanding console program (built here with clang and lld-link) from
  start to exit, then 7-Zip x64's benchmark (`7zr b`), which exercises the translator rather
  than Win32 and compares directly with the 32-bit build and with native.

A freestanding console program (`test/fixtures/hello64.exe`) runs from start to exit
(`hello64.itest.js`), and a program on msvcrt's start-up reads the runtime's and kernel32's
structures in their 64-bit layouts (`crt64.itest.js`). 7-Zip x64 runs its benchmark (`7za b`),
compressing and decompressing, to the end.

## Steps

1. **Decoder:** REX, 64-bit operand and address sizes, the instructions that default to 64 bits,
   RIP-relative addressing, sixteen registers, 64-bit immediates and offsets, the encodings
   64-bit mode drops or redefines. Checked against LLVM's disassembler. Done.
2. **Semantics and a hardware corpus:** the 64-bit reference model, and a corpus made by running
   random instruction sequences natively on an x86-64 host, kept as a fixture. Done for the
   integer set and SSE to SSE3 (`ir64.js`, `tools/x64-corpus.mjs`); x87 and MMX run the
   32-bit model's over the 64-bit state, judged against it on seeded sequences.
3. **Interpreter and translator:** 64-bit registers and flags in the state block (1024 bytes),
   addresses truncated into the window, and the long-mode interpreter over it, in JavaScript
   (`interp64.js`) and as the wasm tier (`interp-wasm.c` built with `LONG`). The translator is
   the 32-bit one at a 64-bit width: one emitter (`emit/region.js` and its integer, memory,
   SSE, MMX and x87 paths, parametric in the width; `emit/long-ops.js` names what forms at 64
   bits) and one runtime (`runtime/runtime.js`). Regions, the entry hash and the transfers
   between them, calls as wasm calls, predicted and formed-in callees, flag liveness, loose
   stacks, wrapped reads, stores into code and the translation store are the same mechanisms
   at both widths. A register is an i64 local, a doubleword write zero-extends, and the
   window's 4 GiB test is folded into the page-flag test (the window's last page is never
   accessible). What is left to the interpreter is what the 32-bit translator leaves: the x87
   environment images and packed BCD, and a string instruction's bulk path (`memory.copy`,
   `memory.fill`), which at 64 bits goes element by element in wasm. Judged against the
   long-mode interpreter on the hardware corpus, on seeded programs of straight code, nested
   loops, MMX, x87 and SSE edges, calls and switches, and on directed cases
   (`runtime/runtime64*.itest.js`, `emit/width64.itest.js`); x87 programs run the same at both
   widths (`x87-width.itest.js` in core). 7-Zip 23.01's benchmark
   (`7za b 4 -md18 -mmt1`, total rating in MIPS) on the project's VM (4-core Xeon @ 2.10 GHz,
   node 22, power plan not recorded), the x64 and the 32-bit build alternated, three runs each:
   x64 2156, 2159, 2122 (median 2156, 57 to 58 s a run), 32-bit 1855, 1874, 1836 (median 1855,
   65 to 66 s): the x64 build runs 16% faster than the 32-bit one.
   Left: the spills of the sixteen registers in large regions, the bulk string paths.
4. **Loader:** PE32+, relocation below 4 GiB, 64-bit TLS and import thunks, the TEB at GS.
   Done but for TLS and delay imports; the TEB and PEB are still laid out as 32-bit ones.
5. **Bridge:** the x64 convention (RCX, RDX, R8, R9, shadow space, XMM0-3); COM tables of
   8-byte slots. Integer arguments and results are done; a quadword argument the 32-bit
   signature counts as two, floating-point arguments, callbacks and hooks are left.
6. **Win32:** the 64-bit layout of every structure a handler reads or writes, starting with what
   a console program and its C runtime need. This is the largest part. A handler learns the
   width from `pointerSize` in its host (`win32/common/pointers.js`). Laid out so far: msvcrt's
   argument and environment arrays, initialiser and exit tables, FILE (48 bytes), the critical
   section (40 bytes), SYSTEM_INFO and the affinity masks. Guest code written as i386 routines
   is a trap in a 64-bit process, where the function has a host handler beside it (critical
   sections, gated against their routines by `critical-paths.itest.js`); a 64-bit routine needs
   the TEB laid out as a 64-bit one first.
7. **Exceptions:** table-based SEH (`.pdata`, `.xdata`), `RtlVirtualUnwind`, `RtlUnwindEx`.
8. **WOW64:** 32- and 64-bit processes side by side; `SysWOW64`, `Wow6432Node`.
