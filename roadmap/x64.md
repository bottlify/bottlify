# x86-64

Plan, work started 2026-10-26.

## Decisions

- **Address space:** a 4 GiB window first. Pointers are 64-bit, every guest page lies below
  4 GiB, and an image whose preferred base is above it (0x140000000 by default) is relocated
  down through its relocations. It runs in every browser, Safari and iOS included, with memory
  accesses as cheap as 32-bit code's. `memory64` is only for a program that needs more than
  4 GiB - an image linked past 4 GiB without relocations, a bottle given 8 GiB - and never the
  default of a 64-bit process (the owner's ruling, 2026-11-18): V8 tests every access to a
  `memory64` memory against its bound, which costs code that works in memory 1.25 to 1.33 times
  its speed over the 4 GiB layout on arm64 (the stand on an M-series Mac and the exact arm64
  counts agree: vm 1.30, fmath 1.33, vcall 1.28), while the 4 GiB layout runs 64-bit code at
  the 32-bit workloads' speed.
- **First targets:** a freestanding console program (built here with clang and lld-link) from
  start to exit, then 7-Zip x64's benchmark (`7zr b`), which exercises the translator rather
  than Win32 and compares directly with the 32-bit build and with native.

A freestanding console program (`test/fixtures/hello64.exe`) runs from start to exit
(`hello64.itest.js`), and a program on msvcrt's start-up reads the runtime's and kernel32's
structures in their 64-bit layouts (`crt64.itest.js`). 7-Zip x64 runs its benchmark (`7za b`),
compressing and decompressing, to the end.

## Steps

1. **Decoder:** REX, 64-bit operand and address sizes, the instructions that default to 64 bits,
   RIP-relative addressing, sixteen registers, 64-bit immediates and offsets, the encodings
   64-bit mode drops or redefines. Checked against LLVM's disassembler. Done.
2. **Semantics and a hardware corpus:** the 64-bit reference model, and a corpus made by running
   random instruction sequences natively on an x86-64 host, kept as a fixture. Done for the
   integer set and SSE to SSE3 (`ir64.js`, `tools/generators/x64-corpus.mjs`); x87 and MMX run the
   32-bit model's over the 64-bit state, judged against it on seeded sequences.
3. **Interpreter and translator:** 64-bit registers and flags in the state block (1024 bytes),
   addresses truncated into the window, and the long-mode interpreter over it, in JavaScript
   (`interp64.js`) and as the wasm tier (`interp-wasm.c` built with `LONG`). The translator is
   the 32-bit one at a 64-bit width: one emitter (`emit/region.js` and its integer, memory,
   SSE, MMX and x87 paths, parametric in the width; `emit/long-ops.js` names what forms at 64
   bits) and one runtime (`runtime/runtime.js`). Regions, the entry hash and the transfers
   between them, calls as wasm calls, predicted and formed-in callees, flag liveness, loose
   stacks, wrapped reads, stores into code and the translation store are the same mechanisms
   at both widths. A register is an i64 local, a doubleword write zero-extends, and the
   window's 4 GiB test is folded into the page-flag test (the window's last page is never
   accessible). What is left to the interpreter is what the 32-bit translator leaves: the x87
   environment images and packed BCD, and a string instruction's bulk path (`memory.copy`,
   `memory.fill`), which at 64 bits goes element by element in wasm. Judged against the
   long-mode interpreter on the hardware corpus, on seeded programs of straight code, nested
   loops, MMX, x87 and SSE edges, calls and switches, and on directed cases
   (`runtime/runtime64*.itest.js`, `emit/width64.itest.js`); x87 programs run the same at both
   widths (`x87-width.itest.js` in core). 7-Zip 23.01's benchmark
   (`7za b 4 -md18 -mmt1`, total rating in MIPS) on the project's VM (4-core Xeon @ 2.10 GHz,
   node 22, power plan not recorded), the x64 and the 32-bit build alternated, three runs each:
   x64 2156, 2159, 2122 (median 2156, 57 to 58 s a run), 32-bit 1855, 1874, 1836 (median 1855,
   65 to 66 s): the x64 build runs 16% faster than the 32-bit one. Both retire nearly the same
   guest instructions a run (x64 124.45 G, 32-bit 125.55 G), so the gain is the speed of an
   instruction (2.18 against 1.90 G a second), not fewer of them; why an x64 instruction runs
   faster is not measured.
   A 64-bit process runs on several executors as a 32-bit one does: the long layout carries the
   processors' fields, and under the atomic variant a `lock`-prefixed instruction or an `xchg`
   with memory is one indivisible access in translated code (`emit/locked.js` `emitLockedLong`,
   judged in `emit/locked64.itest.js`) and in the interpreter (`interp64.js` `evaluateLocked`);
   `locks64.itest.js` in core runs four threads through every locked form on three executors.
   Left to one executor: a process over the wide window. `cmpxchg16b` and an access across two
   aligned quadwords hold the process's lock word (decision A279).
   Left: the spills of the sixteen registers in large regions, the bulk string paths.
4. **Loader:** PE32+, relocation below 4 GiB, 64-bit TLS and import thunks, the TEB at GS.
   Done. The thread and process blocks are laid out in their 64-bit forms (`TEB64`, `PEB64`,
   the loader data and parameter blocks in `kernel32/teb.js`), the block is reached through GS,
   the import thunks are quadwords, and the static thread-local storage and its callbacks run at
   each thread's start and end. The delay-load directory is read and bound at 64 bits too: a
   PE32+ descriptor's thunks are quadwords, an import by ordinal is marked in the thunk's high
   half, and a resolved address is written eight bytes wide.
5. **Bridge:** the x64 convention (RCX, RDX, R8, R9, shadow space, XMM0-3); COM tables of
   8-byte slots. Integer arguments and results are done, a quadword argument the 32-bit signature
   counts as two is read as the one slot it is (`quadwords`), and a routine the host calls back
   runs through the frame `LONG_CALL_CODE` sets up, which is how window procedures, thread
   starts and the exception funclets below are entered. A handler's float and double arguments
   are declared by their first dword (`floats`), and a 64-bit caller's among its first four are
   read from the XMM register of their position into the dwords the 32-bit handler takes them in;
   the runtime's code declares its own from the types its build recorded. A float or a double
   the runtime answers goes to XMM0 rather than ST(0) (`msvcrt/float.js`), and the runtime has
   the float forms a 64-bit msvcrt adds (`sqrtf` and the rest) (`float64.itest.js`). A COM
   interface's word, its table's slots and the pointer QueryInterface writes are eight bytes, and
   a method or count that would run in the guest as i386 code is its trap there
   (`bridge/internal/vtable.js`); a method declares its float arguments as a host function does.
   The bridge's own call hooks (a site hook in the program's code, a hook on an import) have none
   at 64 bits and are refused.
6. **Win32:** the 64-bit layout of every structure a handler reads or writes, starting with what
   a console program and its C runtime need. This is the largest part. A handler learns the
   width from `pointerSize` in its host (`win32/common/pointers.js`). Laid out so far: msvcrt's
   argument and environment arrays, initialiser and exit tables, FILE (48 bytes), the critical
   section (40 bytes), SYSTEM_INFO and the affinity masks, the thread and process blocks
   (above), and the structures of a window program (`user32/structs.js`, `userLayouts`):
   WNDCLASS(EX), MSG, CREATESTRUCT with the CBT hook's block behind it, WINDOWPOS,
   NCCALCSIZE_PARAMS and PAINTSTRUCT, what a CBT, keyboard, mouse or GetMessage hook is handed
   (CBTACTIVATESTRUCT, MOUSEHOOKSTRUCT) and SendInput's 40-byte INPUT (`hook64.itest.js`), and
   GetObject's BITMAP, DIBSECTION, LOGBRUSH and EXTLOGPEN; MINMAXINFO has no pointer and is the
   same at both widths. A 64-bit user32 has
   GetWindowLongPtr, SetWindowLongPtr, GetClassLongPtr and SetClassLongPtr: eight extra bytes
   whole, a field GWLP_ or GCLP_ names sign-extended from the dword the window or class keeps.
   A message's WPARAM and LPARAM keep 32 bits: a procedure is handed a WPARAM zero-extended and
   an LPARAM sign-extended (a hook procedure the same), and an LRESULT, answered at once or
   later, is sign-extended into RAX (`window64.itest.js`). Dialog templates' DWLP_ slots, MDI's MDICREATESTRUCT and the
   control notifications that carry pointers (NMHDR and the rest) are still laid out at 32
   bits. Direct3D 9 draws from a 64-bit process (`d3d9-64.itest.js`): D3DPRESENT_PARAMETERS,
   D3DDEVICE_CREATION_PARAMETERS, D3DLOCKED_RECT and D3DLOCKED_BOX in their 64-bit layouts,
   every interface, locked address and handle an out parameter takes written whole, and
   GetNPatchMode's float answered in XMM0. So does OpenGL (`gl64.itest.js`): each export's
   floats and doubles are declared from its prototype (`opengl/exports.js`, `floatArguments`),
   and the pointer queries write eight bytes. The graphics layer's guest code (the device's
   state block, command ring, getters, counts and lock routines, OpenGL's command ring) is i386
   and off in a 64-bit process, where every call traps. DirectSound plays from a 64-bit process
   (`dsound64.itest.js`): DSBUFFERDESC (24 or 40 bytes) and DSBPOSITIONNOTIFY (16) in their
   64-bit layouts, every interface and locked pointer written whole, and the 3D interfaces'
   D3DVALUE arguments declared as floats. Direct3D 10 and 11 and DXGI are laid out at 64
   bits where a structure holds a pointer, an HWND or a SIZE_T (the subresource data, the input
   layout, the stream-output entries, the maps, the swap chain, adapter and output descriptions),
   their interface outs and arrays eight bytes an entry (`d3d11.test.js`). Direct3D 8 and
   earlier and DirectDraw are not laid out at 64 bits. D3DX 9's textures, buffers and
   shader constant tables answer a 64-bit process: a device's methods from quadword slots,
   every interface written whole, D3DLOCKED_RECT, D3DXMACRO, D3DXCONSTANTTABLE_DESC and
   D3DXCONSTANT_DESC in their 64-bit layouts (`d3dx9/constants.test.js`,
   `d3dx9/texture-tools.test.js`); its effects, meshes, fonts and sprites are not laid out at
   64 bits. Winsock's `hostent` and `fd_set` are laid out at both widths. DirectInput reads a
   64-bit DIDATAFORMAT (32 bytes, its entries 24) and writes 24-byte buffered entries and whole
   interface pointers (`dinput/seam.test.js`); its action maps are not laid out at 64 bits.
   The multimedia timer's thread calls a 64-bit callback in its convention. A 64-bit service
   process connects its dispatcher (SERVICE_TABLE_ENTRY, its argv, QUERY_SERVICE_CONFIG and the
   enumerations in their 64-bit layouts, `advapi32/services.js`), and COM crosses between 64-bit
   processes, and between a 32-bit and a 64-bit one (`com-server.itest.js`, `com64` and
   `comservice64`, the 32-bit fixtures built again for x86-64): the channel reads interface
   pointers, vtable slots and its out-pointers whole, and the typelib marshaler lays a 64-bit
   call out as quadword slots, a VARIANT or a record past eight bytes by reference, VARIANT (24
   bytes), SAFEARRAY, DISPPARAMS and EXCEPINFO in their 64-bit layouts, and loads a library
   registered `win64` first, counting its vtable in quadwords (`oleaut32/marshal.js`, `layoutOf`).
   Not there at 64 bits: a float among a COM method's first three arguments crossing (said and
   refused: a guest call sets no XMM register), the MIDL interpreter a 64-bit proxy/stub DLL is
   built for (`NdrClientCall2`/`NdrStubCall2`, at either width), and the guard that answers
   RPC_E_SERVERFAULT for an exception escaping a method another process called (its frame is
   SEH's, which a 64-bit process does not walk). Visual C++ 2005's C++ library
   answers a 64-bit process under its compiler's names: `std::string` in its 40-byte layout,
   `allocator<char>`, `numeric_limits` and `complex<float>` (`msvcp80.js`), the exception
   classes and `type_info` with quadword fields and vtable slots, `operator new` and `delete`
   (`classes.js`, `longName`). Their run-time type information is not there at 64 bits: a
   64-bit locator names its parts by image offsets, so `typeid` and `dynamic_cast` of one of
   the runtime's own objects find nothing. Guest code written as i386 routines has an x86-64 build beside it, bound in a 64-bit
   process (`scripts/guest-code`): the last-error and thread-id reads, the TLS slot access, the
   critical sections and the interlocked arithmetic run in the guest, gated against their host
   handlers. Real Win64 console programs exercise this: 7-Zip x64 runs its benchmark, hashes a
   file, and adds it to an archive to the end.
7. **Exceptions:** table-based SEH. The unwinder (`kernel32/unwind.js`) reads a function's
   `.pdata` entry and `.xdata` codes and undoes a frame without running its code: the push and
   allocation codes, a frame register, the chained info a funclet carries, and an epilogue
   simulated when the fault is inside one. The dispatcher (`kernel32/seh64.js`) walks the frames
   from a fault or a raised exception, offers each to its language handler, and on acceptance
   unwinds to it. `RtlLookupFunctionEntry`, `RtlVirtualUnwind`, `RtlUnwindEx`,
   `RtlCaptureContext`, `RtlAddFunctionTable` and `RtlDeleteFunctionTable` are exported. The
   runtime's language handlers are interpreted: `__C_specific_handler`'s scope table
   (`seh64.itest.js`; a frame whose own handler hands on to `__C_specific_handler`, as a /GS
   frame's `__GSHandlerCheck_SEH` does, is searched and unwound as if the runtime's were named), and the C++ frame handlers (`msvcrt/eh64.js`) over both layouts of the
   C++ tables, `__CxxFrameHandler3`'s (msvcrt, vcruntime140) and the compressed one
   `__CxxFrameHandler4` reads (vcruntime140_1). Their filters, `__finally` blocks, destructors
   and catch funclets are called as guest code on the stack below the raise, with the frame base
   the convention gives them; a catch funclet's own frame finds the parent's, and a walk leaving
   a catch block goes on in its function at the state the catch left, so a try block does not
   catch twice and an object is not destroyed twice. A language handler that is the program's own
   is called with a DISPATCHER_CONTEXT, as a /GS build's `__GSHandlerCheck_EH` is, and the
   runtime handler it hands the frame on to finds the walk through it; a callback the host made
   is crossed back into the code that called the host. `_setjmp` writes the x64 runtime's
   `_JUMP_BUFFER` (the frame the compiler passes, the kept registers, XMM6 to XMM15, the two
   control words) as guest code, gated against its handler, and `longjmp` reaches a mark that
   kept its frame by an unwind, so the `__finally` blocks between run, taking its registers
   from the buffer (`seh64.itest.js`). `cxxeh64.itest.js` runs one C++ program
   built twice, with each layout of the tables (the build rewrites the compiler's tables into the
   compressed form, `scripts/lib/eh-tables.mjs`). Left: `_set_se_translator`'s translator is kept
   but not called at 64 bits, and the engine's own guest-code routines (msvcrt's `qsort`) have no
   unwind data, so an exception cannot pass through them.
8. **WOW64:** 32- and 64-bit processes side by side; `SysWOW64`, `Wow6432Node`. A run whose
   first program is 64-bit is on a 64-bit Windows (decision A64, `AppOptions.machine`), and a
   64-bit program starts 32-bit and 64-bit children through its 64-bit STARTUPINFO and
   PROCESS_INFORMATION (`wow64.itest.js`). A 32-bit process there runs under WOW64:
   `IsWow64Process` is TRUE of it (another process is judged by its image's headers),
   `GetNativeSystemInfo` names the x64 machine in its 32-bit layout, `GetSystemWow64Directory`
   answers `C:\WINDOWS\SysWOW64` to a process of either width, and the environment carries
   `PROCESSOR_ARCHITEW6432`. The file system redirection (`System32` to `SysWOW64`, `Sysnative`,
   the shared folders, the `Wow64*FsRedirection` calls per thread; `wow64-files.js`), the
   registry's (`Wow6432Node`, the shared keys, `KEY_WOW64_*`; `wow64-registry.js`) and the
   Windows Installer's 64-bit properties and per-component views, and `Program Files (x86)`
   are done 2026-11-20. Left: a 32-bit process's view of a 64-bit one's memory.

## The 8 and 16 GiB windows (`memory64`)

Plan 2026-11-09; steps 1 and 2 in code 2026-11-10. A program that needs 8 GiB is given 8 GiB, one that needs 16
is given 16: the window is a `memory64` memory of that size, not 4 GiB with addresses past it
folded onto it. The first program met that needs it is a 64-bit game whose image has no
relocations and asks for 0x140000000 (`programImage` refuses it today: "cannot be placed below
2 GiB").

What the browser gives, measured 2026-11-09 on the project's VM (16 GB RAM, commit limit 31 GB,
14.5 GB of it free), headless Chrome 157 in a cross-origin isolated page and node 22.21:

- Chrome takes `new WebAssembly.Memory({ initial, maximum, address: 'i64', shared })` with the
  sizes as BigInt; node 22 takes it as `index: 'i64'` with numbers, behind
  `--experimental-wasm-memory64`.
- 8 GiB, plain and shared, grown from one page or made whole: made, and a `Uint8Array` and a
  `DataView` over it read and write past 4 GiB (a byte at 4 GiB + 5, a dword at 8 GiB - 8, the
  last byte).
- 16 GiB plain: made the same. 16 GiB shared grown from one page: refused ("Unable to grow
  instance memory"), in both. 16 GiB shared made whole at once (`initial` = `maximum`): made, and
  read and written past 4 GiB; 10 and 12 GiB the same. So a large shared window is made at its
  size, not grown into.

Steps, each with its tests and gates in the change that makes it:

1. **Layout:** a long-mode layout of 4, 8 or 16 GiB (`windowBytes`), chosen by the process
   (a program's need, an option), the engine's tables where the 4 GiB layout has them.
2. **cork:** addresses as i64 into a `memory64` memory: the emitter's loads and stores, the page
   flags (a table for the larger window), the window test against the window's size instead of
   4 GiB, the near and far branch tests, the helpers module; the long-mode interpreters
   (`interp64.js`, `interp-wasm.c` with LONG, built for wasm64). The 4 GiB layout stays as it is.
3. **Host:** guest pointers past 4 GiB through the bridge and every handler that reads or writes
   guest memory (today they read an argument's low half): the memory module's reads and writes,
   then the layers in the order a program reaches them - loader, kernel32 (virtual memory, files),
   msvcrt, then graphics and sound.
4. **Loader:** an image at its preferred base when the window holds it, relocated or not.

How cork does it (`wideLayout`, 2026-11-10):

- Two memories. The state page and cork's tables stay in memory 0, addressed with 32 bits as in
  4 GiB; the guest's RAM is memory 1, a `memory64` memory of the window's size, its address 0
  the guest's. The page flags and code granules, a byte and two per page of the window, lie
  between the state page and the tables.
- An access keeps its address's low half where the 4 GiB emitter keeps it (`addr`) and the whole
  address in a local of its own (`whole`); a guest access (`ram`, `Body.guest`) goes to memory 1
  at the whole address with the low half it was given (`Body.widenGuest`), written so the engine
  takes the whole address as it stands where the low half is its own. A read goes untested as
  4 GiB's does, its address wrapped into the window; the stack is loose as 4 GiB's is. 4 GiB's
  code is byte for byte what it was.
- The code lies in one 4 GiB block of the window (`codeBase`, the block from 4 GiB for an image
  at 0x140000000). The translator and its runtime keep an instruction's address as its offset in
  the block, 32 bits; the block's start goes into RIP where an address leaves translated code (RIP
  written back, a return address, a RIP-relative operand) and a target outside the block leaves
  for the interpreter. The page table and the runtime's host-facing calls take the window's
  addresses.
- The host is handed a pointer's low dword (`args[i] >>> 0` in a handler). Everything the process
  gives out lies below 4 GiB except the image, so the image's span at its low dword is cut from
  the heap below and is the image's to the host (`hostAlias`): a host access there goes to the
  block from `codeBase`, and the RAM is lent in place to nobody. A pointer past 4 GiB that is not
  into the image (none yet) is `pointerArg`'s, the high dword the bridge passes beside it.
- V8 12 (node 22.21) read `v128.load64_zero`, `load32_zero` and the lane loads from a `memory64`
  memory at a computed address past 4 GiB as zeros. A wide window's code makes them a scalar
  access and a lane operation (`Body.simdScalar`) only where the engine misreads them: each
  runtime over a window asks (`wideLanes`, the ten accesses as translated code makes them, in
  the window's last page) and keeps the access as it is otherwise (2026-11-20: node 22.23, node
  24 and headless Chrome 157 read them right; 1-3 ms a probe). The scalar form cost seven
  machine instructions more a `movss` load: fmath-x64's hottest block 52 machine instructions
  against 19 in 4 GiB, 31 with the access kept. Headless Chrome 157 on the project's VM (x64,
  4 cores; one page, one run of 5 rounds, the 4 GiB layout against the scalar forms and against
  the access kept, over 8 GiB, by time): fmath 1.70 -> 1.30, str 1.44 -> 1.32, tree 1.43 ->
  1.29, game 1.27 -> 1.20, the other 14 within their noise (2-9 %); geomean of the 18 64-bit
  workloads 1.205 -> 1.166. Gate: `runtime64-wide.itest.js` both ways.
- calls4096 over the window, 2026-11-20 (2.47-2.51x by time on an x86 Mac, Chrome 158; exact
  arm64 counts 1.09). Its time is the code's reach, in both layouts: a call costs ~150 ns
  against ~25 in calls512, and a model of 4096 tiny callees called by `call_indirect` in
  scattered order gives the same cliff (node 24: 6 ns a call for 512 callees in modules of 32,
  92 for 4096; 87 for 512 callees each in a module of its own). cachegrind with a Mac's caches
  (32 KiB L1i and L1d, 256 KiB L2; node 24, 200 steady iterations, the difference of a run of
  300 and one of 100): ~10 lines of code a call missed past L2 in 4 GiB, ~12 over the window
  (66.4 M against 79.6 M, 1.20x - the window's callee is 712 bytes of machine code against
  628), data misses and branch mispredictions alike. On the project's VM the window's time is
  1.10-1.46x (headless Chrome 157, five runs) and 1.06x (node 24); neither tiering
  (`--no-liftoff` 1.07, `--liftoff-only` 1.24, `--wasm-tiering-budget=10000` 1.38), inlining
  (`--no-wasm-inlining` 1.33), the engine's bounds checks (`--no-wasm-bounds-checks` 1.22),
  collections (one mark-compact a run in either layout) nor the batches' size (256 regions a
  module: 0.88-1.07 in both) moves it. What the Mac adds past 1.2 is not shown here (page
  walks, which cachegrind does not model, or Chrome 158's code); the lever for both layouts is
  a call's code: a callee of 8 instructions is 126 machine instructions, most of them the
  return's state written back.
- The interpreter tier in wasm runs over the window as over 4 GiB (`interp-wasm.c` built with
  LONG and WIDE, `interp-wasm-wide.bytes.js`): an address is a quadword whole, and the hash, the
  hot counts and the ring know code by its offset in the code block. C cannot name a second
  memory and clang compiles every access to memory 0, so the source reaches the guest through
  functions imported from `ram` and the build (`scripts/ram-memory.mjs`) puts the load, store,
  copy or fill of memory 1 where each call was; an instruction's bytes are copied into memory 0
  to be decoded. Its gate is `interp-wasm-wide.itest.js`: the corpus, calls, switches, loops and
  seeded programs on the tier alone against `interp64.js`, the data and the code past 4 GiB.
- Where the space ends, 2026-11-19. What the system places for the program (thread and process
  blocks, stacks, libraries, the C runtime's structures, COM objects: `low64.itest.js`) lies in
  the 2 GiB layout every process has; the heap and VirtualAlloc's pages go on from there to
  4 GiB less 128 KiB (`HEAP_SIZE` in app.js), so a process over the window has about 3.7 GiB to
  take (58 blocks of 64 MiB in `memory64.itest.js`; 27 before, when the heap ended at 2 GiB).
  2026-11-24: the window's RAM past 4 GiB is handed out once the space below has no room
  (A289; 122 blocks of 64 MiB in `memory64.itest.js`, 63 of them past 4 GiB). A block there
  given to a system call whose handler takes the pointer's low dword would be read and written
  4 GiB below - 2568 of 8390 handlers still differ past 4 GiB
  (`tools/checks/wide-addresses-high.json`) - so the bridge says such a call a loss
  (`watchCut`) instead of letting it pass quietly; the list is what is left to make whole.
- Code outside the code block, measured 2026-11-19 (`jit64.exe` at 0x140000000 with no
  relocations against the same file placed low; exact machine instructions of the whole run,
  qemu, node 26, start-up of ~0.5 G in each): the code block is the image's, so everything
  below 4 GiB is run by the interpreter tier - and that is not only a JIT's pages but every
  system library's own code. A loop copied into executable pages: 36.0 M of 36.0 M guest
  instructions interpreted, 9962 M machine instructions against 565 M (277 a guest instruction
  against 15.7). `strlen` 100 000 times: 53.5 M of 54.4 M interpreted, 13 259 M against 656 M
  (244 against 12.1). `HeapAlloc` + `HeapFree` 100 000 times: 7.9 M of 9.3 M interpreted and
  three exits to the host a round, 6555 M against 674 M (705 against 72). The same loop in the
  image: 622 M against 528 M. So the policy of placing a JIT's pages in the image's block
  would leave the larger part - the C runtime, the heap, Direct3D's routines, all below 4 GiB
  by the rule above - interpreted: the translator needs code in two blocks (the block below
  4 GiB and the image's), with an instruction's address a block and an offset.
- Code in two blocks, 2026-11-19: the core's host gives the block below 4 GiB a runtime of its
  own beside the image's (`twoBlockRuntime` in cork-host.js; cork's `wideLayout` with
  `codeBase` 0 and its tables past the first's; `lowBlock: false` turns it off). A RIP picks the
  runtime. A return, an indirect jump or an indirect call whose target lies in the other block
  is made in translated code and leaves with a far exit (`FAR` plus the target's high half in
  the exit's vector, put back into RIP by the runtime); the host's loop enters the other
  runtime there. A run's stores into code (the window's stale span) are told to both runtimes,
  and the interpreter tier in wasm counts and enters the block below 4 GiB through that
  runtime's hash, while translated code resumes after the tier only at an entry of its own
  block. jit64.exe, exact machine instructions a guest instruction over the window (low layout
  in brackets): the loop copied into executable pages 277 -> 17.1 (15.4), `strlen` 244 -> 27.2

## A value's width at the bridge

A 64-bit caller reads a whole register where a 32-bit one read a dword, so the bridge widens each
value by its type, declared once in the spec beside its signature comment and held to it by
`tools/checks/check-wide-arguments.mjs`:

- A result that is an address or an unsigned size (`returns: 'pointer'`: a pointer, HMODULE,
  FARPROC, SIZE_T, by the comment's return type) goes into RAX zero-extended; every other dword is
  sign-extended (INVALID_HANDLE_VALUE, LRESULT). A spec a helper makes says it where it is made
  (`{ ...make(...), returns: 'pointer' }`) or passes it to the helper.
- A callback's argument is a dword widened by its JavaScript sign (an address given unsigned is
  zero-extended) or a bigint, the quadword whole: an argument that came into the host whole goes
  back whole.
- An argument that is an address the handler hands on or keeps - a module's instance, a
  parameter for a callback, a name written back into a structure - is declared on the spec
  (`addresses: [dwords]`) and handed over whole, low + high * 2^32, where its high half names an
  address (not zero, below 2^21); any other high half leaves the dword every handler has always
  had, so a process in 4 GiB sees no change. `check-wide-arguments.mjs` holds each declared dword
  to an address of the signature above the spec. A handler that declares one keeps it with
  `wholeAddress`, never `>>> 0`. Every function is declared its addresses from its signature
  comment (`common/pointer-arguments.js`, `declareAddresses`; a spec's own declaration wins), and
  the helpers that read and write guest memory for a handler (strings, guest code's memory at
  64 bits, the common `readDword` / `readText` shapes) take the address whole; an answer typed
  an address reaches RAX whole (`unsignedAddress`). A window's and a class's procedure, module
  and names are kept and answered whole (GetWindowLongPtr, GetClassLongPtr, WNDCLASS,
  CREATESTRUCT); the arrays of comctl32 (DPA, DSA) and a completion port's key and OVERLAPPED
  are the x86-64 layout.
  A value that is any quadword (a LONG_PTR, an LPARAM) is a `quadwords` argument, both halves.
- A value the host only hands on is the program's whole. A message's WPARAM and LPARAM stay
  dwords inside user32 (a WPARAM widened as the UINT, an LPARAM as the LONG); what a 64-bit
  caller passed that the dwords do not say - a pointer past 2 GiB in an LPARAM, whose high half
  is zero and not its sign's ones, and any value past 4 GiB - rides beside the message (`wide`,
  `common/pointers.js` `wideOf` / `paramsOf`) through SendMessage, the posted queue and MSG, to
  the procedure; the procedure's LRESULT comes back the same way (`wholeAnswer`: the callback's
  RAX high half is on its promise, a handler may answer a bigint after a wait). An enumeration's
  context and an APC's parameter go as `forwarded` gives them.
  SendMessageTimeout (its DWORD_PTR result whole), SendNotifyMessage, SendMessageCallback,
  PostThreadMessage and CallWindowProc carry them alike. A timer's id is whole (two ids that
  differ past the dword are two timers; WM_TIMER's WPARAM and the TIMERPROC's id carry it, the
  TIMERPROC itself may lie past 4 GiB), CallNextHookEx hands on what the hook passed, and the
  contexts of EnumDesktopWindows, EnumDesktops, EnumWindowStations, EnumFontFamilies(Ex),
  EnumFonts and EnumResourceTypes / Names / Languages reach their callbacks whole.
- Left: a message to another process, the parameters the host makes for a hook (a structure it
  places), contexts of enumerations not named above; found by `check-wide-addresses.mjs --high
  0x1_4000_0000` and by the fixtures. A handler that reads through a pointer past 4 GiB reaches
  the image through its low alias today. An answer that comes after a wait (a promise, a
  handler's steps) is widened as one in place is: an address by zeros, any other dword by its
  sign (`lateAnswer`, the frame's `zeroExtends`); a wait the kernel itself ends (a
  WaitForSingleObject's status) is a dword by its sign. SetWindowLongPtr keeps a GWLP_WNDPROC or
  GWLP_HINSTANCE past 4 GiB whole, and CallWindowProc calls such a procedure where it is. A
  handler that cuts an address it declared whole back to a dword fails `check-wide-arguments`.
- A size is eight bytes to a 64-bit caller. A handler that takes one as a dword declares it
  (`sizes: [dwords]`), and the bridge hands a size past a dword as the largest dword, which the
  handler refuses as any request too large: malloc, calloc, realloc, the aligned family,
  operator new, GlobalAlloc, LocalAlloc and their ReAllocs, CoTaskMemAlloc, VirtualAllocEx.
  Undeclared, 4 GiB + 16 bytes was answered with a block of sixteen. HeapAlloc, HeapReAlloc and
  VirtualAlloc read theirs whole (`pointerArg`). The rest of the C runtime's `size_t`
  arguments (counts of bytes to copy, compare, format) are not declared yet.
