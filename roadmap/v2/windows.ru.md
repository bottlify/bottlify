# Оконный менеджер запуска

English version: [windows.md](windows.md).

**Статус:** план, кода нет. 2026-10-05, относительно `cork2` 1ad2506c. Часть второго этапа v2;
идёт раньше пулов переводчиков. Пути к файлам — от `modules/core/src/`, если не сказано иное.

## Зачем

Сами окна user32 в порядке; плохо то, что построено вокруг них, чтобы вывести несколько процессов
на один экран. Окно существует только внутри создавшего его процесса
(`layers/win32/user32/windows.js`); запуск знает его хэндл, владельца, класс и заголовок
(`user32/directory.js`), и больше ничего. Поэтому всё, где участвуют окна двух процессов,
решается правилом, которое их не учитывает:

- **Экран** — кадр того процесса, который пришёл последним (`webgpu/internal/presenter.js`,
  `show`), и холст принимает размер этого кадра; каждый процесс рисует свой полноэкранный рабочий
  стол, а его кадры не говорят, чьи они. Графический воркер держит один слот `newest` на кадры
  Direct3D всех клиентов. Родитель перерисовывает всё, когда дочерний процесс завершается
  (`app.js`, `refreshWindows`).
- **Ввод** уходит процессу, запущенному последним (`app.js`, `facade.input`, `across().at(-1)`).
- **Активация** своя у каждого процесса; каждый считает, что других активных программ нет
  (WM_ACTIVATEAPP). `GetForegroundWindow`, `WindowFromPoint` и `EnumWindows` отвечают за один
  процесс.
- **Z-порядка** между процессами нет.

И показать окно не может никто, кроме GDI: вид, отличный от пикселей самого гостя, — страница,
которая сама рисует контролы диалога, окно на окно, — не имеет ни состояния, которое можно
прочитать, ни способа узнать об изменении.

## Устройство

user32 остаётся как есть. Он сообщает запуску о своих окнах; запуск держит то, что может знать
только он; виды показывают окна по тому, что держит запуск.

### 1. Что процесс сообщает запуску

В тех местах, где user32 уже меняет окно, — `makeWindow`, `forget`, `place` (SetWindowPos,
MoveWindow, BringWindowToTop, DeferWindowPos), `showNow` (ShowWindow), `raise`, `restack`,
`activateNow`, SetWindowText, — он публикует состояние окна менеджеру запуска вызовом без ожидания:

```js
// WindowState: что запуск знает об окне
{ hwnd, processId, threadId, parent, owner, className, title, style, exStyle,
  rect, client,          // координаты экрана
  visible,               // оно и его предки
  enabled, minimized, maximized, topmost, region }
```

Состояние дочерних окон тоже публикуется, чтобы у вида было всё дерево. Три места, которые сейчас
меняют окно в обход всего этого, — `SetWindowPlacement`, `SetWindowLong(GWL_STYLE)` с
переключением WS_VISIBLE и `windowService.place`, — идут через `place`, и заодно получают
перерисовку, которой у них нет.

### 2. Оконный менеджер запуска (`user32/manager.js`)

На системном потоке, один на запуск, рядом с каталогом окон. Он держит:

- все окна всех процессов, как их публикует каждый процесс;
- z-порядок окон верхнего уровня всех процессов: слой topmost выше остальных, окно с владельцем
  выше владельца;
- активное окно (foreground) и окно, захватившее мышь;
- ревизию, которая сдвигается с каждым изменением.

```js
manager.publish(state) / manager.remove(hwnd)   // что сообщает процесс
manager.raise(hwnd) / manager.lower(hwnd) / manager.insertAfter(hwnd, after)
manager.setForeground(hwnd)              // → извещения процессам, теряющему и получающему
manager.setCapture(hwnd) / manager.releaseCapture()
manager.get(hwnd) / manager.topLevel()   // окна верхнего уровня запуска в z-порядке
manager.fromPoint(x, y)                  // по всем процессам
manager.foreground() / manager.capture()
manager.subscribe(listener)              // каждое изменение по порядку: (event) => void
manager.command(hwnd, request)           // запрос вида, переданный процессу окна
```

То, что знает только запуск (активное окно, окно в точке, порядок окон других процессов), процесс
спрашивает у менеджера блокирующим запросом, как сейчас спрашивает каталог окон. Изменение чужого
окна — SetWindowPos или ShowWindow на хэндле, которым процесс не владеет, — передаётся процессу-
владельцу и делается там его user32, как Windows отправляет его потоку-владельцу.

### 3. Виды

Вид — всё, что показывает окна: он подписан на менеджер и никогда не лезет в процесс. Он может
отправлять запросы обратно (`manager.command`): окно перетащили, нажали кнопку закрытия, щёлкнули,
— а менеджер передаёт их процессу-владельцу как ввод или сообщение, которое сделала бы Windows.

- **GDI-склейка**, первой: кадры каждого процесса — слой с меткой источника; экран собирается из
  слоёв по окнам верхнего уровня менеджера, снизу вверх, каждое с ножницами по своему
  прямоугольнику минус то, что выше, остальное — фон рабочего стола. Холст размером с экран.
  Графический воркер держит слот `newest` на каждого клиента.
- **Маршрутизация ввода**: мышь — окну под курсором или захватившему её, клавиатура — процессу
  активного окна.
- **JS view**, потом: те же события дают ему всё дерево — классы, заголовки, стили,
  прямоугольники, порядок, — чтобы показывать окно или стандартный контрол элементом страницы, а
  пиксели гостя брать только там, где их рисует гость.

## Шаги

Каждый шаг приходит со своими тестами; перед попаданием в `cork2` прогоняется полный набор.

1. **Менеджер и то, что сообщают процессы.** `manager.js` с состоянием, общим z-порядком (слой
   topmost, окно с владельцем выше владельца), `subscribe` и таблицей диагностики; публикация из
   мест изменения user32, три прямых изменения переведены на `place`. Гейт: случайные
   последовательности оконных вызовов в одном и в двух процессах, и после каждого состояние
   каждого окна в менеджере равно тому, что держит user32 его процесса (`list()`), при concurrency
   1, 2 и 4.
2. **Активация и вопросы между процессами.** Активное окно и захват принадлежат менеджеру;
   процессу, который теряет или получает активность, об этом сообщается (WM_ACTIVATE,
   WM_ACTIVATEAPP с потоком другой программы); `GetForegroundWindow`, `WindowFromPoint`,
   `EnumWindows` и `GetWindow` отвечают за весь запуск; изменение чужого окна делает его владелец.
   Тесты: фикстура из двух процессов, которые поднимают и активируют окна друг друга и проверяют,
   что им сообщают, при concurrency 1, 2 и 4.
3. **Склейка.** Кадры с источником, слот на клиента в графическом воркере, слои, собранные по
   менеджеру, холст размером с экран. Гейт: эталонная склейка на CPU и склейка на GPU дают
   одинаковые пиксели на случайных раскладках окон двух и трёх процессов; itest: два процесса с
   перекрывающимися окнами, экран считан и сравнён.
4. **Ввод.** Мышь — окну под курсором или захватившему её, клавиатура — процессу активного окна.
   Тесты: ввод приходит нужному процессу в фикстуре из двух процессов.
5. **Хаки уходят.** `refreshWindows` при выходе, «последний кадр побеждает», холст размером с
   каждый кадр, ввод самому новому процессу, активация на процесс. `docs/core/` и
   `docs/architecture.md` описывают менеджер и API видов.

## Готово, когда

Тесты шагов проходят при concurrency 1, 2 и 4, ни одного из хаков шага 5 не осталось, а в браузере
лаунчер и запущенная им игра, а также инсталлятор с дочерними процессами показывают окна всех
процессов одновременно и в их порядке. Проверка в браузере — за человеком; здесь она не
измеряется.
