# Оконный менеджер запуска

English version: [windows.md](windows.md).

**Статус:** план, кода нет. 2026-10-05, относительно `cork2` 1ad2506c; заменяет первый вариант того
же дня (общее на запуск зеркало окон каждого процесса). Часть второго этапа v2; идёт раньше пулов
переводчиков. Пути к файлам — от `modules/core/src/`, если не сказано иное.

## Зачем

Окно сейчас существует только как запись внутри создавшего его процесса
(`layers/win32/user32/windows.js`, `Map` `windows`), и её правят на месте там, где это нужно вызову:
около 130 мест в `windows.js`, `system.js` и `frame.js` прямо присваивают `x`, `y`, `width`,
`height`, `style`, `parent` или `owner`. Нет состояния окна, которое мог бы прочитать кто-то ещё,
нет операции, которая меняет его целиком, и нет извещения об изменении. Запуск знает хэндл окна,
владельца, класс и заголовок (`user32/directory.js`), и больше ничего. Поэтому:

- **Экран** — кадр того процесса, который пришёл последним (`webgpu/internal/presenter.js`,
  `show`); каждый процесс рисует свой полноэкранный рабочий стол, а его кадры не говорят, чьи они.
  Графический воркер держит один слот `newest` на кадры Direct3D всех клиентов. Родитель
  перерисовывает всё, когда дочерний процесс завершается (`app.js`, `refreshWindows`).
- **Ввод** уходит процессу, запущенному последним (`app.js`, `facade.input`).
- **Активация** своя у каждого процесса; каждый считает, что других активных программ нет
  (WM_ACTIVATEAPP). `GetForegroundWindow`, `WindowFromPoint` и `EnumWindows` отвечают за один
  процесс.
- **Z-порядок** — порядок вставки в `Map` одного процесса; слоя topmost нет, а `HWND_BOTTOM` окно
  верхнего уровня не двигает.
- **Изменения, о которых никто не знает:** `SetWindowPlacement`, `SetWindowLong(GWL_STYLE)` с
  переключением WS_VISIBLE и `windowService.place` правят запись и ничего не перерисовывают.

И показать окно не может никто, кроме GDI: вид окон, отличный от пикселей самого гостя, —
страница, которая сама рисует контролы диалога, окно на окно, — не имеет ни состояния, которое
можно прочитать, ни способа узнать об изменении.

## Устройство

Три части, у каждой одна задача.

### 1. Модель окон (`user32/model.js`)

Модель дерева окон на чистом JavaScript с семантикой Win32, без памяти гостя и без сообщений. Любое
изменение окна — одна из её операций, и каждая операция возвращает изменения, которые сделала. В
ней процесс держит свои окна.

```js
const model = createWindowModel({ screen: () => ({ width, height }) });

// операции: каждая возвращает сделанные изменения, [] — если ничего
model.create({ hwnd, parent, owner, className, title, style, exStyle, rect, thread }) // Change[]
model.place(hwnd, { rect?, insertAfter?, flags })   // SetWindowPos: флаги SWP_*, значения HWND_*
model.show(hwnd, command)                           // ShowWindow: команды SW_*
model.setStyle(hwnd, style, exStyle?)               // GWL_STYLE / GWL_EXSTYLE, включая WS_VISIBLE
model.setText(hwnd, text)
model.setParent(hwnd, parent) / model.setOwner(hwnd, owner)
model.enable(hwnd, enabled)
model.destroy(hwnd)                                 // окно и все его потомки

// вопросы
model.get(hwnd)            // WindowState, неизменяемый: hwnd, parent, owner, className, title,
                           // style, exStyle, rect (в клиентских координатах родителя), screenRect,
                           // clientRect, visible (оно и предки), enabled, minimized, maximized,
                           // topmost
model.children(hwnd)       // в z-порядке, верхнее первым; hwnd 0 — окна верхнего уровня
model.fromPoint(x, y)      // самое глубокое видимое окно под точкой
model.uncovered(hwnd)      // его видимая область на экране, прямоугольниками
```

`Change` — это `{ kind: 'created' | 'placed' | 'shown' | 'hidden' | 'stacked' | 'styled' |
'retitled' | 'reparented' | 'enabled' | 'destroyed', hwnd, before, after }`. Активация, фокус и
захват мыши — не модели: они принадлежат потоку и запуску (ниже).

user32 перестаёт присваивать записям. Его функции API вызывают операции модели, а то, что
сообщается программе, — WM_WINDOWPOSCHANGING и CHANGED, WM_MOVE, WM_SIZE, WM_SHOWWINDOW,
WM_STYLECHANGING и CHANGED, последствия WM_SETTEXT, перерисовка открывшегося — строится из
изменений, которые вернула операция, в одном месте. В записи остаётся только своё у процесса:
процедура, класс, дополнительные байты, свойства, область обновления.

### 2. Оконный менеджер запуска (`user32/manager.js`)

На системном потоке, один на запуск, рядом с каталогом окон. Он держит:

- все окна всех процессов, как их публикует модель каждого процесса: после каждой операции процесс
  отправляет свой `Change[]` вызовом без ожидания;
- z-порядок окон верхнего уровня всех процессов: слой topmost выше остальных, окно с владельцем
  выше владельца;
- активное окно (foreground) и окно, захватившее мышь;
- ревизию, которая сдвигается с каждым изменением.

```js
manager.apply(processId, changes)        // что сделала модель процесса
manager.raise(hwnd) / manager.lower(hwnd) / manager.insertAfter(hwnd, after)
manager.setForeground(hwnd)              // → извещения процессам, теряющему и получающему
manager.setCapture(hwnd) / manager.releaseCapture()
manager.get(hwnd) / manager.topLevel()   // окна верхнего уровня запуска в z-порядке
manager.fromPoint(x, y)                  // по всем процессам
manager.foreground() / manager.capture()
manager.subscribe(listener)              // каждое изменение по порядку: (event) => void
manager.command(hwnd, request)           // запрос вида, переданный процессу окна
```

То, что знает только запуск (активное окно, окно в точке, порядок окон других процессов), процесс
спрашивает у менеджера блокирующим запросом, как сейчас спрашивает каталог окон. Изменение чужого
окна — SetWindowPos или ShowWindow на хэндле, которым процесс не владеет, — передаётся процессу-
владельцу и делается там его моделью, как Windows отправляет его потоку-владельцу.

### 3. Виды

Вид — всё, что показывает окна: он подписан на менеджер и никогда не лезет в процесс. Он может
отправлять запросы обратно (`manager.command`): окно перетащили, нажали кнопку закрытия, щёлкнули,
— а менеджер передаёт их процессу-владельцу как ввод или сообщение, которое сделала бы Windows.

- **GDI-склейка**, первой: кадры каждого процесса — слой с меткой источника; экран собирается из
  слоёв по окнам верхнего уровня менеджера, снизу вверх, каждое с ножницами по своему
  прямоугольнику минус то, что выше, остальное — фон рабочего стола. Холст размером с экран.
  Графический воркер держит слот `newest` на каждого клиента.
- **Маршрутизация ввода**: мышь — окну под курсором или захватившему её, клавиатура — процессу
  активного окна.
- **JS view**, потом: те же события дают ему всё дерево — классы, заголовки, стили,
  прямоугольники, порядок, — чтобы показывать окно или стандартный контрол элементом страницы, а
  пиксели гостя брать только там, где их рисует гость.

## Шаги

Каждый шаг приходит со своими тестами; перед попаданием в `cork2` прогоняется полный набор.

1. **Модель.** `model.js` с операциями и вопросами; контракт — из документированного поведения
   Windows и конформанс-тестов user32 из Wine (`dlls/user32/tests/win.c`: SetWindowPos,
   ShowWindow, z-порядок, стили). Юнит-тесты на каждую операцию и валидатор в `tools/`: ни один
   файл user32 не присваивает геометрию, стиль, родителя или владельца окна в обход модели.
2. **user32 на модель.** Геометрия, стиль, родитель, владелец, видимость и порядок записей
   переходят в модель; около 130 присваиваний становятся операциями; сообщения строятся из
   изменений. Идёт частями (положение, затем показ, затем стили, затем родитель и владелец), каждая
   за гейтом: случайные последовательности оконных вызовов, прогнанные старым путём и через
   модель, сравнивают всё, что видит программа, — ответы, сообщения и их параметры по порядку,
   список окон, пиксели рабочего стола, — и старый путь уходит, когда его часть закрыта гейтом.
3. **Менеджер.** `manager.js`, публикация из каждого процесса, общий z-порядок со слоями, активное
   окно и захват с извещениями об активации обоим процессам, вопросы между процессами и
   `subscribe`. Тесты: собственные юнит-тесты менеджера и фикстура из двух процессов, которые
   поднимают и активируют окна друг друга и проверяют сообщения, при concurrency 1, 2 и 4.
4. **Склейка и ввод.** Кадры с источником, слот на клиента в графическом воркере, слои,
   собранные по менеджеру; ввод направляется им. Гейт: эталонная склейка на CPU и склейка на GPU
   дают одинаковые пиксели на случайных раскладках окон двух и трёх процессов. itest: два процесса
   с перекрывающимися окнами, экран считан и сравнён.
5. **Убрать то, что это заменяет.** `refreshWindows` при выходе, «последний кадр побеждает», ввод
   самому новому процессу, активация на процесс. `docs/core/` и `docs/architecture.md` описывают
   менеджер и API видов.

## Готово, когда

Тесты шагов проходят при concurrency 1, 2 и 4, состояние окна нигде не присваивается в обход
модели (валидатор), а в браузере лаунчер и запущенная им игра, а также инсталлятор с дочерними
процессами показывают окна всех процессов одновременно и в их порядке. Проверка в браузере — за
человеком; здесь она не измеряется.
